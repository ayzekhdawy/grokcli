## 批次 A（P0）：Changes/Diff 数据丢失

三条核心问题都在 `src/components/resource-viewer/useResourceDiffActions.ts`（#578 引入），共享同一根因：**内容来源回退链不校验「当前打开的 diff 是否属于目标文件」**。必须一个 PR 一起修。

### A1 [Critical] accept 跨文件写错内容

- **位置**：`useResourceDiffActions.ts:142-150`（`runAcceptFile`）。
- **根因**：`after` 回退链 `afterOverride ?? diffView?.afterText ?? restorableAfterByPath[key]` 中，`diffView.afterText` 没有 `normalizePath(diffView.path) === key` 守卫（同函数 `executeRejectFile` 里 `before` 在 202-206 行有这个守卫，`after` 漏了）。workspace 行的 accept 按钮不传 override（`ResourceChangesList.tsx:553`），session 行快照缺失时传 `null` 也会落进回退链。
- **触发**：预览打开 A 的 diff → 对列表里的 B 点 accept → B 被写成 A 的全文。
- **修复**：
  1. `runAcceptFile` 的 `diffView?.afterText` 分支加 `normalizePath(diffView.path) === key` 条件；
  2. 无路径匹配来源时返回 `null`，让 `planFileAccept` 走 `keep_current` / `unavailable` 分支（`src/lib/diffAccept.ts` 已支持）。
- **关联修改**：
  - 建议把「内容来源选择」抽成纯函数（如 `resolveDiffAfterSource(diffView, key, override, cache)`）放进 `src/lib/diffAccept.ts`，A1/A2 共用；
  - `src/lib/diffAccept.test.ts` 增加用例：打开 A 的 diff 时对 B accept → `keep_current`。
- **验证**：单测 + 手工（开 A 的 diff，对 B accept/reject/restore，确认 B 内容不变）。

### A2 [Major] reject 污染 Restore 缓存

- **位置**：`useResourceDiffActions.ts:195-201`（`executeRejectFile`）。
- **根因**：与 A1 同——`after` 无路径守卫，`rememberRestorable(path, after)` 会把 A 的内容存到 B 的 key 下；`runRestoreFile`（约 :377）优先读缓存，后续对 B 点 Restore 就写入 A 的内容。
- **修复**：使用 A1 抽出的同一个带路径守卫的来源函数。
- **验证**：单测覆盖「缓存永远只存本路径内容」。

### A3 [Critical] 逐 hunk accept 还原其他 hunk 且销毁恢复副本

- **位置**：`useResourceDiffActions.ts:418-464`（`runAcceptHunk`）。
- **根因**：三个叠加缺陷——
  1. 写盘内容是 `applySelectedHunks(before, hunks, [i])` = 快照 + 单个 hunk，磁盘上其他所有 hunk 被静默还原，且无确认；
  2. `rememberRestorable` 在**写盘后**执行、存的是 partial 内容，把缓存里唯一的完整 after 也覆盖 → 双副本同时丢失；
  3. 写盘后不重建 `diffView`（对比 `runRejectHunk` 在 508-524 有 `setDiffView`），连续 accept 第二个 hunk 会撤销第一个。
- **修复**（保留「partial accept = 丢弃其余」的产品语义时）：
  1. 写盘**前** `rememberRestorable(diffView.path, diffView.afterText)`（保存完整磁盘态，Restore 可回退）；
  2. 弹 GlassModal 确认：「接受此块并丢弃其余 N 块修改？」（新 i18n key ×3 语言，例如 `changes.acceptHunkConfirm`）；
  3. 写盘成功后重建 `diffView` / unified（新 after = `result.content`，重算 hunks），保证连续操作可组合。
  - 备选方案：把 hunk accept 改成纯标记（磁盘不动，只有 reject hunk 写盘）。语义更安全但改变现有交互，需产品决策；默认按上面三步修。
- **关联修改**：`runRejectHunk` 的缓存时机顺带核对（它先 `rememberRestorable` 再写盘，是正确参照）；`diffAccept.test.ts` 增加连续 accept 组合用例。
- **验证**：手工——3 个 hunk 的文件依次 accept 两个，确认磁盘内容 = 快照 + 两个 hunk；Restore 能回到完整修改态。

### A4 [Minor] 全脏标签 LRU 丢弃无确认

- **位置**：`src/lib/resourceTabs.ts:109-123`（`pickResourceTabLruDropIndex`）、`:249-257`（`openResourceTab`）。
- **修复**：当唯一可丢弃候选是 dirty 时，`openResourceTab` 拒绝打开新标签并返回 soft-fail 通知（新 i18n key，如 `resources.tabsMaxAllDirty`），而不是丢弃脏标签。
- **关联修改**：`resourceTabs.test.ts` 更新全脏用例；调用方（`useResourceFileTabs.ts`）处理新的拒绝分支。

### A5 [Minor] hunk 操作强加末尾换行

- **位置**：`src/lib/diffAccept.ts:100-103`（`joinPatchLines`）。
- **修复**：`applySelectedHunks` / `rejectSelectedHunks` 记录源内容 `endsWith("\n")`，重组时保留原状态。
- **关联修改**：`diffAccept.test.ts` 增加无末尾换行文件的用例。

## 批次 C（P0）：Voice

### C1 [Critical] Live Voice 覆盖层监听器一次重渲染后永久失效

- **位置**：`src/components/VoiceOverlay.tsx:334-541`（订阅 effect）+ `src/app/AppWorkbench.tsx:21471`（`onClassifiedNotice={(m) => showToast(m, 4800)}` 内联箭头）。
- **根因**：effect 用 `started.current` 防重入（:346-347），但 deps 含 `noticeClassified`（间接依赖内联 prop，每次父渲染变身份）。父组件一渲染 → cleanup 退订全部 `voice://*` / `session://permission` 监听（:521-529）→ effect 重跑碰到 `started.current === true` 直接 return，**不再订阅**。委派会话往 `liveMap` 推流必然触发父渲染，等于功能上线即失效；麦克风推流却不停。
- **修复**：
  1. `AppWorkbench.tsx:21471`：`onClassifiedNotice` 用 `useCallback`（`showToast` 本身稳定）；
  2. `VoiceOverlay.tsx`：把 `appendLine` / `applyToolEvent` / `noticeClassified` / `tt` 放进 ref（渲染时同步 `.current`），effect deps 收敛为 `[open, projectPath, projectId, projectName, voiceId, keepAgentsOnEnd]`；
  3. 顺带修异步注册竞态：effect 内 `let cancelled = false`，cleanup 置 true；每次 `await` 后注册前检查 `cancelled`，已注册的立即退订（当前 `unsubs` 在两个 `await` 之后才填充，早期 churn 会泄漏订阅）。
- **关联修改**：无纯函数可测，手工验证为主。
- **验证**：打开 Live Voice → 触发父组件重渲染（切换任意会话状态）→ 说话仍有转写/音频/工具事件；关闭后监听与麦克风都释放。

### C2 [Major] 听写自动发送间歇失效

- **位置**：`src/app/AppWorkbench.tsx:9751-9764`。
- **根因**：是否发送取决于 `setDraft` updater 内部对 `inserted` 的副作用赋值；React 在 fiber 有 pending update 时延迟执行 updater（流式渲染时几乎必然），`if (commit.kind === "send" && inserted.trim()…)` 读到空串 → 只插入不发送。
- **修复**：删除 `inserted` 旁路，直接 `if (commit.kind === "send")`。依据：`resolveDictationCommit` 已对空文本返回 `empty`（`voiceDictation.ts:366-367`），`planTranscriptInsert` 仅对空转写返回 `null`（:335-336），send 分支不可能是无操作插入。updater 保持纯净。
- **验证**：开启自动发送，在 agent 流式输出期间听写 → 稳定发送。

- **关联修改**：
