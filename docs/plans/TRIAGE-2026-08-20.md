## 4. Issue #735 — macOS 绿色放大按钮死锁（P0，自修）

### 根因（已在源码级确认，非猜测）

经典 AB 锁死锁，两把「锁」分别是 window-state 插件的 cache mutex 和 macOS 主线程：

- **A（tokio 线程）**：`src-tauri/src/lib.rs:1651` `schedule_persist_main_window_state` 在 `tauri::async_runtime::spawn` 的任务里（debounce 400ms 后）调 `persist_main_window_state` → 插件 `save_window_state`。插件源码（`tauri-plugin-window-state 2.4.1` `lib.rs:127`）**先拿 cache mutex**，随后持锁调用 `window.is_maximized()` / `inner_size()` / `outer_position()`（`lib.rs:283–315`）。这些 getter 在 macOS 上从非主线程调用会**同步派发到主线程并阻塞等待**。
- **B（主线程）**：点绿色按钮触发 maximize，产生一连串 `Resized`/`Moved` 事件。插件自己注册的 `on_window_event`（插件 `lib.rs:447–449`）在主线程上对每个事件 **拿同一把 cache mutex**（`Moved` 分支是 `lock()` 不是 `try_lock()`）。
- 时序：上一次 resize 的 400ms debounce 刚到期 → tokio 线程持锁等主线程；主线程在 maximize 事件风暴中等锁 → 冻死。绿色按钮最容易踩中是因为 maximize 动画产生密集 Resized，且事件处理时间长，撞上 debounce 到期窗口的概率最大。与 issue 里 4 份卡死报告描述完全一致。

### 修复（1 个文件，改动 ~5 行）

`src-tauri/src/lib.rs:1650–1664`，把 debounce 到期后的落盘从 tokio 线程搬回主线程：

```rust
/// Debounced disk flush after resize/move (coalesces rapid drag events).
fn schedule_persist_main_window_state(app: &tauri::AppHandle) {
    use std::sync::atomic::{AtomicU64, Ordering};

    static GENERATION: AtomicU64 = AtomicU64::new(0);
    let gen = GENERATION.fetch_add(1, Ordering::Relaxed) + 1;
    let app = app.clone();
    tauri::async_runtime::spawn(async move {
        tokio::time::sleep(std::time::Duration::from_millis(400)).await;
        if GENERATION.load(Ordering::Relaxed) != gen {
            return;
        }
        // macOS deadlock guard (#735): save_window_state holds the plugin's
        // cache mutex while querying window geometry. Off the main thread the
        // getters block on the main thread, which may itself be waiting on
        // that mutex inside the plugin's Resized handler. Hop back first.
        let app2 = app.clone();
        let _ = app.run_on_main_thread(move || persist_main_window_state(&app2));
    });
}
```

主线程上锁只会被主线程自己拿（插件事件 handler 与本次 save 串行执行），getter 也不再跨线程派发，死锁两条边同时消失。

### 为什么不会改坏其他路径

- 其余两个调用点本来就在主线程：`lib.rs:448`（CloseRequested handler）、`tray.rs:225`（`hide_to_tray`，托盘菜单事件在主线程）。行为不变。
- `run_on_main_thread` 是投递（主线程忙时排队执行），不阻塞 tokio 线程，debounce 语义不变。
- Windows/Linux 不受影响（那里 getter 不跨线程阻塞），但统一走主线程也无害。

### 验证与回归

- macOS：反复点绿色按钮 maximize/还原 ≥20 次、拖拽窗口边缘连续 resize、maximize 后立即 ⌘W 隐藏到托盘——不冻。
- 退出重开确认窗口几何仍能恢复（`.window-state.json` 有新 mtime）。
- `cd src-tauri && cargo test && cargo fmt --check`。
- 提交信息带 `Fixes #735`；CHANGELOG Unreleased「修复」加一条（en+zh）。

## 5. Issue #734 — 手机镜像 dist not found（P1，自修）

### 根因（源码级确认）

`src-tauri/src/mirror/mod.rs:518–538` `resolve_dist_dir` 找 SPA 静态目录的三条路都在打包后的用户机器上**必然失败**：

1. `env!("CARGO_MANIFEST_DIR")/../dist` —— **编译期**烙进二进制的构建机路径（CI runner / 开发机），用户机器上不存在；
2. cwd 相对的 `dist/`、`../dist/` —— 打包 app 的 cwd 是 `/` 或 app bundle，也不存在；
3. `GROK_MIRROR_DIST` 环境变量 —— 终端用户不可能设。

于是 `serve_index`（`mirror/http.rs:237–258`）读不到 `index.html`，永远返回占位页「Mirror host online (dist not found)」。开发模式（`pnpm tauri dev`，仓库根有 `dist/`）能用，**所有正式安装包上镜像功能 100% 坏**——这不是环境问题，是发布形态下的必然。

### 修复方案：从 Tauri 内嵌资源兜底（推荐）

打包后前端已经以 `frontendDist` 形式嵌在二进制里，Tauri v2 提供 `app.asset_resolver().get(path)` 直接取（返回字节 + mime）。镜像 host 在 `mirror_start` 时已经 `attach(app, mgr)` 拿到了 `AppHandle`（`mod.rs:553`），管道是现成的。

改动三处：

1. **`src-tauri/src/mirror/http.rs`** — `HttpState` 加 `app: Option<AppHandle>`（`start_server` 多传一个参数）。新增：

```rust
/// Packaged fallback: filesystem dist missing → embedded frontendDist.
fn serve_embedded(app: &AppHandle, rest: &str) -> Option<(Vec<u8>, String)> {
    let key = format!("/{}", rest.trim_start_matches('/'));
    let asset = app.asset_resolver().get(key)?;
    Some((asset.bytes.to_vec(), asset.mime_type))
}
```

   - `serve_index`：`std::fs::read_to_string` 失败后，先试 `serve_embedded(app, "index.html")`，拿到 HTML 就照走 `inject_mirror_shell(&raw, &token)` + `html_no_store`（token 注入、no-store 语义不变），两者都失败才回占位页；
   - `serve_static_file` 改为先试文件系统（保留现有 canonicalize 防穿越逻辑），miss 时试 `serve_embedded`。嵌入资源 key 是固定集合，不查文件系统，无穿越风险，但保留现有 `..`/`\\`/前导 `/` 拒绝逻辑再进 resolver；
   - `public_assets_handler` 同样加兜底（`/assets/*` 哈希 chunk 是移动端加载主体，漏了它页面还是白）。

### 8.1 PR #750 — Windows 跟随系统主题（Fixes #749）✅ 本批次先合

**根因**（issue 与代码互证成立）：启动时 Host 为对齐 WebView2 表单控件颜色调 `window.set_theme(Some(Light|Dark))`，这会**冻住** WebView2 里的 `prefers-color-scheme`；前端只订了 `matchMedia`，系统个性化翻转永远到不了 `data-theme`。macOS 无此问题（走 null Auto + WKWebView matchMedia 活的）。

**方案质量**：结构做得对——
- 把 `os_prefers_dark` 从 `lib.rs` 抽到新模块 `src-tauri/src/os_theme.rs`（顺带把 Windows 探测从 `reg query` 子进程换成 `winreg` 直读，更快无窗口闪烁；`lib.rs` 净减 50 行，符合质量整治方向）；

### 8.2 PR #748 — Windows 托盘深色任务栏隐身（Fixes #747）⚠️ 两处修改后合

**根因**（成立）：托盘用 `tray-32.png`（透明底黑标）；macOS 有 `icon_as_template(true)` 自动反色，Windows 没有模板机制，黑标叠深色任务栏直接隐身。方案是生成一对高对比徽章（浅任务栏黑底白标 / 深任务栏白底黑标），跟随 `SystemUsesLightTheme`（任务栏主题，**不是**应用内主题——判断正确），1s 轮询热切换。徽章生成脚本 + Python 测试 + Rust 内嵌像素断言都齐，`icons.md` 双管线文档也更新了，i18n 不涉及。依赖 `winreg`/`image` 已在 `Cargo.toml`（91/67 行），无新依赖。

**必须改的一处：跨线程 `set_icon` 重演 #735 死锁模式。** `watch_taskbar_theme` 的后台线程里 `apply_tray_icon` 先 `tray.lock()`（`Mutex<TrayIcon>`）再 `t.set_icon(...)`——Windows 上 tray 操作最终要回到事件循环线程执行。若主线程此刻正好在拿同一把 `Mutex<TrayIcon>`（例如 `tray_set_busy_count` 命令、忙碌徽章更新），就是「后台线程持锁等主线程、主线程等锁」的同型 AB 死锁（§4 刚在 macOS 修过一模一样的结构）。**要求**：把 `apply_tray_icon` 用 `app.run_on_main_thread(...)` 包起来执行，轮询线程只做检测与去重。
