# 目标模式 vs 定时任务 — 产品优化与用户建议（交接）

**日期**：2026-08-11  
**状态**：问题诊断 + 产品建议 + 可直接转交用户的操作指南  
**范围**：Grok App（Composer Goal、已安排）与 Grok Build（`/goal`、`/loop`、`scheduler_*`）的概念分流  
**不在范围**：具体业务站点（如奥德赛）的页面改版实现

---

## 1. 问题一句话

用户想要的是：**在同一会话里按产品原则持续工作，直到本轮可验收**。  
系统却容易落到：**按时间间隔再跑一遍提示词**（定时任务 / loop / 已安排）。

根因不是「功能坏了」，而是 **三种「持续」通道撞名、语义相近、工具选型默认偏向时钟**。

---

## 2. 概念模型（产品必须先分清）

| 通道 | 用户心智 | 系统实际 | 结束条件 | 典型入口 |
|------|----------|----------|----------|----------|
| **A. 会话原则 / 角色契约** | 「从现在起你按这套规则陪我」 | 上下文 / 项目规则 / 记忆，**被动**约束每条回复 | 用户改规则或新开会话 | `AGENTS.md`、粘贴原则、记忆 |
| **B. Goal（有限目标）** | 「把这件事干完并证明干完了」 | `/goal` harness：多轮规划 → 执行 → 对抗验收 | 验收通过 / pause / budget | Composer「目标」chip、消息前缀 `/goal` |
| **C. 定时 / 已安排** | 「到点再做 / 周期性巡检」 | App 已安排、`/loop`、`scheduler_create` | 时间表；loop 约 7 天过期；once 一次 | 侧栏「已安排」、`/loop`、自动化 fence |

### 错误映射（当前易发）

| 用户说 | 模型常理解成 | 正确通道 |
|--------|--------------|----------|
| 「开启目标模式」+ 长角色卡（始终/每次/维护…） | C 定时常驻 或 半吊子 B | **A**（原则）± 有具体活时再 **B** |
| 「一直帮我盯着主线」无截止 | C | 有验收 → **B**；真巡检 → **C** |
| Composer 打开 Goal 再贴角色原则 | B 有限 objective（形状不对） | 原则走 **A**；任务走 **B** 且要可完成表述 |

### 关键产品原则

1. **「目标」= 有限可验收 objective**，不是「永久角色开关」。  
2. **「定时」= 时钟触发**，不是「连续干完」。  
3. **开放维护型文案默认不要自动进 C**；若进 C，必须二次确认并换文案（「已创建定时任务」）。  
4. **删减歧义优先于再加一层引导 UI**。

## 3. 产品侧优化建议（Grok App / Build 体验）

按优先级排列；每条可独立排期。

### P0 — 防误建：默认不把「模式/原则」做成定时任务

| 项 | 建议 | 验收 |
|----|------|------|
| **P0-1 创建调度前确认** | Agent 调用 `scheduler_create` / 输出 `grok-automation` fence / 等价 `/loop` 前，若用户原文含「模式/原则/角色/始终/从现在起」且**未**含明确时间（每天/每 N 分钟/点钟），先问一句：「要做成定时任务，还是只在本会话按规则工作？」 | 无明确时间表述时，不会静默出现「已安排」toast |
| **P0-2 自动化 fence 二次确认（可选策略）** | 非「用 AI 创建已安排」入口的会话：解析到 fence 后弹应用内确认，而不是直接 `automation_create` | 普通聊天误输出 fence 不会直接落库 |
| **P0-3 硬否定词** | 用户写「不要定时 / 不要 loop / 禁止 schedule」时，Host 或系统前缀注入禁止调度工具（或强约束文案） | 该会话不再创建 schedule |

### P0 — 文案与命名：消灭撞名

| 项 | 现状风险 | 建议 |
|----|----------|------|
| **P0-4 Goal chip 文案** | 「目标模式」被理解成常驻角色 | 中文改为 **「目标任务」** 或 **「/goal 干完即停」**；副文案：「有限目标 · 多轮验收 · 不是定时 · 不是永久角色」 |
| **P0-5 已安排 vs Goal 对照** | 用户分不清侧栏「已安排」和 Composer Goal | 已安排空态 / 创建引导加一句：**「周期性或到点执行 → 已安排；同一会话连续干完 → 用 Goal」** |
| **P0-6 Toast 诚实** | 「已安排：xxx」出现时用户以为是目标模式开了 | Toast 用 **「已创建定时任务」**，并链到已安排页；禁止用「目标」字样 |

### P1 — Goal 通道：让「干完」更像干完

| 项 | 建议 | 验收 |
|----|------|------|
| **P1-1 Goal 开启引导** | 第一次开 Goal chip 时短提示：需可完成目标 + 验收标准；开放「维护/始终」会提示改写成 objective 或改走规则 | 用户能复述「Goal ≠ 定时」 |
| **P1-2 形状检查（软）** | 发送内容过长且无动词交付物时，弱提示：「更像角色说明。原则可放项目规则；Goal 请写本轮要完成什么」 | 不阻断发送，可关闭 |
| **P1-3 中途勿静默转 loop** | Goal 进行中禁止模型擅自 `/loop` 续跑；应 `goal pause` + 说明缺口，或请用户继续 | Goal 会话 timeline 无意外 cron |
| **P1-4 完成态** | 验收通过后明确 chip：已完成 / 可 clear；区分「回合结束」与「目标完成」 | 用户不会以为「停了所以挂了定时」 |

### P1 — 会话原则通道：给「目标模式」一个正名出口

用户真正想要的「产品搭档模式」目前**没有一等公民**，只好挤 Goal 或挤定时。

| 项 | 建议 |
|----|------|
| **P1-5「会话规则」入口（轻）** | Composer「+」或设置：粘贴/启用一段 **Session instructions**（只进上下文，不创建 task/schedule） |
| **P1-6 与项目规则分工** | 文案写清：跨会话长期 → `AGENTS.md` / 项目规则；仅本会话 → Session instructions |
| **P1-7 模板** | 提供「产品北极星搭档」模板：原则 + **禁止 schedule** + 「具体改动请另开 /goal 或直接发任务」 |

不必做重型「模式引擎」；**一等公民的「只约束、不调度」** 就能消掉大半误路由。

### P2 — 可观测与自救

| 项 | 建议 |
|----|------|
| **P2-1 会话活动条** | 若存在 loop/scheduler/已安排关联本会话，状态行写清「定时唤醒仍在」，与 Goal chip 分开展示 |
| **P2-2 一键取消** | 「取消本会话全部定时 / loop」入口（对齐 `scheduler_list` + delete + 已安排禁用） |
| **P2-3 Doctor / 可靠性** | 增加检查项：本会话 goal 状态、活跃 loop、App 已安排数量；避免「空 Goal chip + 背后在跑 cron」 |
| **P2-4 文档** | 用户指南一页三列表（原则 / Goal / 定时），App 内链到已安排与 Goal 说明 |

### 明确不做（反模式）

- 不要用「再加任务条 / 步骤轨 / 弹层」掩盖三种通道的混淆。  
- 不要把用户自定义长角色卡自动升级成 durable 定时任务。  
- 不要让 Goal 与 已安排 共用「目标」一词。  
- 不要在无用户明确时间意图时默认 `frequency: daily`。

### 建议里程碑

| 波次 | 内容 | 成功标准 |
|------|------|----------|
| **M1** | P0 文案 + Toast +（可选）fence 确认 | 支持工单里「目标变定时」误建率明显下降 |
| **M2** | P1 Goal 引导 + 禁 Goal 内静默 loop + Session instructions 轻入口 | 用户能稳定完成「原则常驻 + 任务用 Goal」 |
| **M3** | P2 可观测与一键清理 | 误建后 30 秒内可自救 |

## 4. 给用户的建议（可整节转发）

> 下面从「你要什么」出发，不写实现黑话。可直接复制给使用者。

### 4.1 先选对工具（30 秒决策）

| 你想要的结果 | 请用 | 不要用 |
|--------------|------|--------|
| 从现在起每条回复都按某套产品原则说话 | **会话/项目规则**（粘贴原则，或写入项目 `AGENTS.md`） | 已安排、每天循环 |
| 把一件事**连续做完**并对照验收 | **Goal（目标任务）** 或普通对话多轮改到满意 | 定时任务 |
| 每天 / 每 N 分钟自动再跑一遍 | **已安排** 或 `/loop` | Goal 角色长文 |

**口诀**：  
- **原则** = 一直生效的说明书  
- **Goal** = 干完即停的任务单  
- **定时** = 闹钟  

### 4.2 不要这样开「目标模式」

容易变成定时任务的说法：

- 「开启目标模式」+ 整篇「始终 / 每次 / 维护…」长文，且没有「本轮完成标准」  
- 「一直帮我优化主线」没有截止  
- 打开 Goal 开关后，把**角色说明书**当成**唯一一条消息**发送  

### 4.3 推荐这样用

#### 只要长期原则（搭档怎么思考）

1. 把原则放进项目规则 / `AGENTS.md`，或本会话第一条只贴原则。  
2. 文末加一句硬约束（建议原样保留）：

```text
【执行约束】
- 这是会话原则，不是定时任务。
- 禁止创建 /loop、scheduler、已安排、grok-automation。
- 有具体改动时在本会话连续执行到可验收；不要用闹钟续跑。
```

3. **不要**打开「已安排 → 用 AI 创建」来贴原则。

#### 本轮有具体要完成的事（推荐）

用 **Goal**，并写成「可完成 + 可验收」：

```text
/goal 收敛主线体验：点燃 → 进厅 → 主线 3 洞可闭环。
成功标准：
1) 用户能口述这三步；
2) 同一屏只有一个主动作；
3) 通识/匹配/十火图不与开场抢入口。
禁止：创建任何定时任务、/loop、已安排。
做完对照成功标准说明如何验收，再结束。
```

原则若已在项目规则里，Goal 消息里**只写本轮交付**，不必每次贴全文。

#### 真的需要定时

说清时间与动作，例如：

- 「每天 09:00 检查线上是否仍是单主动作主线，只报告回归」  
- 或侧栏 **已安排 → 手动/AI 创建**，并核对频率与文案  

创建成功后应看到 **「定时 / 已安排」** 类提示，而不是「目标模式已开启」。

### 4.4 已经变成定时任务时怎么处理

1. 打开侧栏 **「已安排」**：暂停或删除刚创建的任务。  
2. 若在 CLI/TUI：查看 loop/scheduler 列表并取消对应任务。  
3. 回到原对话，用 **§4.3** 的写法重开：**原则用规则，任务用 Goal，并写上禁止定时**。  
4. 需要接着改产品时，发一条**短 objective**，不要再贴整篇「始终维护」长文当 Goal。

### 4.5 自检清单（发之前 10 秒）

- [ ] 我有没有写「每天 / 每小时 / 点钟 / 定期」？有 → 才是定时。  
- [ ] 我有没有写「完成标准 / 验收 / 做完即停」？有 → 适合 Goal。  
- [ ] 我是不是只想「以后你都按这套想」？→ 原则/规则，不要 Goal 也不要定时。  
- [ ] 是否写了「禁止 loop / 已安排 / scheduler」？（开放维护类强烈建议写）  
- [ ] 发出后若出现「已安排 / 定时任务」toast → 按 §4.4 撤销，不要当成功。

### 4.6 给协作方的短说明（可贴群）

```text
Grok 里三件事不要混：
1) 产品原则 / 角色 → 会话或项目规则（一直生效，不是任务）
2) 本轮要干完的活 → Goal / 普通连续对话（干完即停）
3) 到点或周期性 → 已安排 / loop（闹钟）

「开启目标模式」+ 长文「始终维护」最容易被做成 3)。
正确：原则进规则 + 禁止定时；具体改版用带验收的 /goal。
```

## 6. 残留风险（产品知情）

1. **只要模型仍可在普通会话输出 `grok-automation` fence 且壳层自动 apply**，误建定时的路径就还在；P0-2 是结构性补丁。  
2. **用户语言里的「目标模式」无法靠产品单独消灭**；没有「只约束不调度」的轻入口（P1-5）时，仍会挤占 Goal 或定时。
